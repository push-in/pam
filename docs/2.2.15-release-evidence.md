# PAM 2.2.15 release evidence

Combined `main` after #156 (listener handoff), #153 (post-boot zygote), #154
(edge page cache) and #155 (Swoole parity), release build (`cargo build
--release`, PHP 8.5.12 embedded), binary built from `2c0700da`, whose tree is
identical to `main` at `e23ca552` (squash of #155). Intel Core Ultra 9 185H,
30 GiB, Linux 7.0.11, `net.ipv4.tcp_migrate_req=0` on the host. The machine
was shared with other workloads (load average 13 to 34 during the runs).

## Integration finding (fixed in #155 before merge)

With the four branches combined, 6 of the 8 Swoole-parity matrix checks failed
(shared `octane` cache, `concurrently()` on task workers, task dispatch,
ticks, cache intervals, survival across reload): the post-boot zygote boots
the application before PAM knows which forks become task workers, and while
the master is blocked waiting for that boot. Root causes and fixes
(in #155):

- the zygote did not get the shared-memory and task environment, so tables and
  the shared cache were not attached while booting: it now does;
- a table opened while booting timed out (`cannot receive shared memory:
  EAGAIN`) because the shared memory server ran on the master's
  current-thread runtime, which is blocked in the zygote's first fork: the
  server now runs on its own thread (unit test without any runtime);
- forked task workers ran the HTTP handler: `PamServer` now takes the task
  handler per request in a task worker, and Rust raises the body limit to the
  64 MiB task limit. Task workers stay zygote siblings, so idle-first task
  balancing still applies (exec'ing them instead, tried first, lost it:
  `concurrently()` ran 2 tasks on 1 task worker).

After the fix: 8/8 on Laravel 12 and 13.

Two more fixes found while rebasing: the PHP static analysis of the page
cache and shared-table code (`phpstan` level 9, stubs for the native
functions), and a race in the listener-ownership test from #156 (a draining
worker of the previous generation no longer holds a listener; the test now
waits for it to exit).

## Soak (zygote ON, `tcp_migrate_req=0`, Laravel 12, 4 HTTP + 2 task workers)

`tools/parity_soak.py` mixes shared-table increments, shared-cache reads,
cache misses, `Octane::concurrently()` on task workers and plain requests
under `wrk`, and checks every table increment.

**30 minutes, chaos:** `--seconds 1800 --reload-every 60 --chaos --kill-every 15 --max-requests 2000`

- 7,604,767 requests, 29 reloads, `--max-requests` recycling of every worker,
  `kill -9` of 75 HTTP and 42 task workers.
- 1,281 failed (0.017 %), all caused by the `kill -9`s: 1,147 socket read
  errors on the keep-alive connections the killed HTTP workers held (about 15
  per kill: every connection of the killed process, no accept-queue loss since
  the master keeps the listener) and 134 `concurrently()` calls whose task
  worker was killed mid-task (the Laravel log has exactly 134 "task request
  failed" errors and nothing else). The server log has no other error.
- Table increments exact (2,390,230 answered, 2,390,250 applied: requests in
  flight when a worker was killed or at the deadline), then 20,000/20,000 in
  the exact run; 0 table repairs.
- Memory flat from minute 5 to 30 (PSS totals): HTTP workers 49-79 MB, task
  workers 18-27 MB, zygote 33-44 MB (106 MB while two zygotes overlap during a
  reload), master 2-5 MB.

**10 minutes, zero-loss:** `--seconds 600 --reload-every 30 --max-requests 2000`, no kills

- 2,806,838 requests, 19 reloads, recycling of every HTTP and task worker,
  162,475 `concurrently()` calls: **0 failed** (0 socket errors, 0 non-2xx),
  increments exact.

## Errors attributable to PAM

None in the final runs. Everything that failed during this work was
root-caused: the zygote/task-worker integration and the two CI fixes above;
the soak failures are the `kill -9`s themselves.
